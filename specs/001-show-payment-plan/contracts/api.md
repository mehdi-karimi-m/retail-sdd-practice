# API Contract: نمایش محصول و برنامه

نسخهٔ قرارداد 1.2.0؛ قالب [OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3.html)؛ قرارداد ماشینی: [openapi.json](openapi.json).

## درخواست‌ها

| روش و مسیر | ورودی | خروجی موفق |
| --- | --- | --- |
| GET /api/product | بدون body یا احراز هویت؛ query ناشناخته نادیده گرفته می‌شود | نام، قیمت و واحد تومان |
| POST /api/product/payment-plan/validity | JSON snapshot قبلی: baseDate و expiresAt | فقط نتیجهٔ اعتبار و زمان سرور؛ بدون محاسبهٔ برنامه |
| GET /api/product/payment-plan | بدون body یا احراز هویت؛ query ناشناخته نادیده گرفته می‌شود | محصول و برنامهٔ کامل با تاریخ امروز تهران |

هیچ endpoint عمومی برای تعیین قیمت، تاریخ خرید، سود، تعداد اقساط یا ایجاد محصول وجود ندارد.
baseDate در validity فقط شناسهٔ روز snapshot قبلی برای بررسی اعتبار است، نه تاریخ خرید انتخابی.
queryهای ناشناخته نادیده گرفته می‌شوند و نتیجه را تغییر نمی‌دهند؛ body نامجاز روی دو GET یا بدنهٔ نامعتبر validity، 400 با
code=invalid_request است؛ endpointهای دیگر 404
و روش‌های دیگر روی همین مسیرها 405 می‌دهند. برای تغییر قیمت/تاریخ در تست از DI استفاده شود،
نه query یا header مخصوص آزمون. هر پاسخ این سه مسیر Cache-Control: no-store داشته باشد.

## موفقیت

JSON UTF-8؛ نام‌ها camelCase. مبلغ همیشه رشتهٔ ASCII بدون اعشار، علامت یا جداکننده است.
`currency=TOMAN`؛ صفر فقط برای سود/کارمزد مجاز است. `baseDate` و `dueDate` شمسی‌اند و
ISO/Gregorian نیستند؛ format=date در OpenAPI روی آن‌ها نباید گذاشته شود.

محصول:

```json
{
  "name": "محصول نمونه",
  "priceToman": "1000000",
  "currency": "TOMAN"
}
```

برنامه، نمونهٔ قطعی آزمون با ساعت ثابت؛ تاریخ واقعی پاسخ از روز درخواست به وقت تهران می‌آید:

```json
{
  "product": { "name": "محصول نمونه", "priceToman": "1000000", "currency": "TOMAN" },
  "currency": "TOMAN",
  "calendar": "persian",
  "timeZone": "Asia/Tehran",
  "baseDate": "1405/07/16",
  "serverTime": "2026-10-08T12:00:00Z",
  "expiresAt": "2026-10-08T20:30:00Z",
  "downPaymentToman": "300000",
  "installments": [
    { "number": 1, "amountToman": "175000", "dueDate": "1405/08/16" },
    { "number": 2, "amountToman": "175000", "dueDate": "1405/09/16" },
    { "number": 3, "amountToman": "175000", "dueDate": "1405/10/16" },
    { "number": 4, "amountToman": "175000", "dueDate": "1405/11/16" }
  ],
  "totalPaymentToman": "1000000",
  "interestToman": "0",
  "feeToman": "0"
}
```

## اعتبار زمانی و بررسی snapshot

serverTime و expiresAt فیلدهای الزامی RFC3339 UTC با Z هستند؛ serverTime زمان مرجع
ساخت پاسخ از ساعت بک‌اند است؛ expiresAt نیمه‌شب شروع روز بعد baseDate در تهران.
این timestampها میلادی‌اند و به سررسید شمسی هیچ قسطی تبدیل نمی‌شوند.

فرانت‌اند RTT درخواست تا دریافت/parse کامل را با performance.now ثبت کند و از اختلاف
expiresAt−serverTime کسر کند؛ باقی‌مانده با ساعت یکنواخت کم شود. کسر تمام RTT محافظه‌کارانه
است (حداکثر یک RTT زودتر از مرز واقعی) و با ساعت تقویمی دستگاه مقایسه نمی‌شود. بودجهٔ
صفر یا منفی هرگز مجوز نمایش نمی‌دهد. اگر round-trip از مرز تعلیق/غیرفعال‌شدن عبور کند،
بودجهٔ آن پاسخ مجوز ready نیست؛ پس از بازگشت در دورهٔ فعال تازه با سرور بررسی شود. Date.now برای انقضا و RTT ممنوع است.

POST /api/product/payment-plan/validity، بدون احراز هویت و اثر جانبی:

```json
{ "baseDate": "1405/07/16", "expiresAt": "2026-10-08T20:30:00Z" }
```

پاسخ نمونه با ساعت ثابت سرور، status=200:

```json
{
  "baseDate": "1405/07/16",
  "serverTime": "2026-10-08T12:00:00Z",
  "expiresAt": "2026-10-08T20:30:00Z",
  "isValid": true
}
```

فقط دو فیلد درخواست، هر دو الزامی؛ فیلد اضافه، تاریخ شمسی غیرواقعی/خارج از محدوده،
JSON خراب یا expiresAt غیر UTC Z برابر 400 invalid_request است. expiry صحیح از روز
ارسالی در سرور استخراج شود؛ baseDate غیر امروز، expiry ناسازگار یا serverTime>=expiry
برنامه را نامعتبر می‌کنند (200 با isValid=false). expiresAt پاسخ مقدار استاندارد سرور
برای همان baseDate است. endpoint هیچ calculator اقساطی را صدا نمی‌زند و مبلغ/اقساط/محصول
در پاسخ ندارد؛ ماندگاری یا token خرید ایجاد نمی‌شود. query ناشناخته همچنان بی‌اثر است.

هنگام بازگشت از تعلیق/تب غیرفعال، برنامه تا پاسخ اعتبار معتبر و بودجهٔ مثبت در checking
پنهان باشد؛ true فقط همان snapshot را بازنمایش می‌دهد، false حالت expired است. خطا، timeout
یا پاسخ بدشکل verification-error است و برنامه پنهان می‌ماند. تلاش مجدد بررسی فقط POST
validity است؛ GET برنامه فقط با اقدام «محاسبهٔ دوباره» ارسال شود. بررسی اعتبار خودکار مجاز
است، محاسبهٔ برنامهٔ تازه خودکار مجاز نیست. پاسخ‌های قدیمی snapshot تازه را تغییر ندهند.

## اعتبارسنجی و خطا

محدودهٔ دامنه علاوه بر schema باید در backend بررسی شود: قیمت صحیح ۵ تا ۱۰۰ میلیارد،
چهار قسط مثبت، برابری جمع و سررسیدهای معتبر. schema رشته یا شکل تاریخ به‌تنهایی کافی نیست.
نام خالی محصول نیز دادهٔ نامعتبر است. ورودی قیمت منبع decimal دقیق و nullable است؛
مقدار مفقود، کسری، صفر، منفی یا خارج از دامنه پیش از تبدیل به long رد شود. parser عمومی
متن/NaN/Infinity لازم نیست؛ مدل typed این مقادیر را نمی‌پذیرد. API ورودی قیمت ندارد.

| وضعیت | code | کاربرد |
| --- | --- | --- |
| 400 | invalid_request | body نامجاز GET یا بدنهٔ نامعتبر validity |
| 404 | product_not_found | محصول نمونه در منبع موجود نیست |
| 500 | invalid_product | نام/قیمت منبع نامعتبر؛ قیمت زیر ۵ شامل اقساط صفر |
| 500 | calculation_failed | overflow، invariant خراب، تاریخ خارج از محدوده |
| 500 | internal_error | خطای غیرمنتظره، با جزئیات فنی فقط در لاگ سرور |

خطاها application/problem+json و دارای type، title فارسی، status، detail فارسی و code
پایدار هستند؛ فقط type، title، status، detail و code طبق required قرارداد الزامی‌اند.
`errors` اختیاری است؛ نبود آن پاسخ خطای معتبر را نامعتبر نمی‌کند. اگر موجود باشد، باید
object با مقادیر آرایهٔ رشته‌ها (`Record<string, string[]>`) باشد؛ null، آرایه به‌جای object
یا مقدار غیرآرایه/عضو غیررشته رد شود. status JSON با HTTP برابر باشد.
برای مسیرهای ناشناخته و روش نامجاز نیز ProblemDetails با not_found/method_not_allowed
تولید شود. هیچ پاسخ خطا نباید در کنار خود برنامهٔ ناقص داشته باشد.

```json
{
  "type": "about:blank",
  "title": "اطلاعات محصول معتبر نیست",
  "status": 500,
  "detail": "قیمت باید تومان صحیح بین ۵ و ۱۰۰ میلیارد و دارای چهار قسط مثبت باشد.",
  "code": "invalid_product",
  "errors": { "priceToman": ["قیمت خارج از دامنهٔ مجاز است."] }
}
```

## نمایش و مرز فرانت‌اند

نام و قیمت از محصول، برنامه فقط با درخواست سرور. در پاسخ برنامه snapshot محصول دوباره
ارسال می‌شود تا نام/قیمت نمایش‌داده‌شده با برنامه یکسان باشد. برچسب‌ها: «پیش‌پرداخت»،
«قسط اول» تا «قسط چهارم»، «سررسید»، «مجموع پرداخت»، «تاریخ مبنای پیش‌نمایش»،
«بدون سود و کارمزد». مبلغ رشته‌ای با گروه‌بندی سه‌رقمی، ارقام فارسی و پسوند «تومان» نمایش
داده شود. تاریخ‌های شمسی فقط تبدیل ارقام نمایشی دارند؛ در مرورگر محاسبه یا parse زمانی
نشوند. serverTime و expiresAt، timestampهای UTC مجزا برای تعیین بودجهٔ زمانی هستند.

runtime parser قبل از حالت ready فقط ساختار پاسخ، شکل رشتهٔ مبلغ و تاریخ، serverTime و expiresAt
معتبر UTC، metadata و شماره‌های چهار قسط را بررسی کند. کنترل دامنهٔ مالی و جمع فقط در
بک‌اند و تست قرارداد است؛ هیچ جمع پول، BigInt یا محاسبهٔ جایگزین در مرورگر لازم نیست.
TypeScript type assertion به‌تنهایی validation نیست.

Loading پیام انتظار قابل فهم دارد؛ error پیام فارسی با امکان تلاش مجدد. نام و قیمت
قبلاً دریافت‌شدهٔ معتبر حفظ شوند، اما برنامهٔ قبلی هنگام درخواست تازه، خطا یا انقضا کنار
گذاشته شود. تلاش مجدد محاسبه فقط GET برنامه و تلاش مجدد بررسی فقط POST validity است. خطای شبکه یا JSON خراب پیام عمومی «نمایش برنامه
در حال حاضر ممکن نیست» بدهد. پیام‌های ProblemDetails تنها به‌صورت متن نمایش داده شوند.
