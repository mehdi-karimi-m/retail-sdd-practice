# Test Design: استخراج از معیارهای پذیرش

این سند طراحی آزمون است؛ فایل تست یا implementation ندارد. مقادیر expected باید ثابت
باشند و با اجرای Calculator تحت آزمون تولید نشوند. شمارهٔ سناریوها به spec.md ارجاع دارد.

## محاسبات، xUnit

| قیمت P | پیش‌پرداخت D | هر یک از سه قسط اول B | قسط چهارم L | سناریو |
| --- | --- | --- | --- | --- |
| 1000000 | 300000 | 175000 | 175000 | ۲ |
| 1000010 | 300003 | 175001 | 175004 | ۳؛ باقی‌ماندهٔ ۳ تومان |
| 1000001 | 300000 | 175000 | 175001 | ۷؛ پیش‌پرداخت کسری |
| 5 | 1 | 1 | 1 | ۱۲؛ مرز پایین |
| 100000000000 | 30000000000 | 17500000000 | 17500000000 | ۱۳؛ مرز بالا |

هر ردیف باید علاوه بر پنج مبلغ، جمع دقیق، مثبت بودن چهار قسط، سود/کارمزد صفر و عدم
overflow را اثبات کند (FR-003 تا FR-007، FR-013، SC-002). برای D rounding، expected را
از جدول بردارید، نه از تبدیل double. کنترل اضافی روی نمونه‌های قیمت صحیح معتبر: سه قسط
اول برابر، اختلاف L با B بین صفر و سه، جمع مساوی P. این کنترل مکمل مثال‌های ثابت است.

| ورودی عددی منبع (decimal?) | انتظار | سناریو |
| --- | --- | --- |
| 1، 2، 3، 4 | رد؛ چهار قسط مثبت ممکن نیست | ۱۴ |
| 0، -1 | رد | ۱۵ |
| 5.5 (decimal) | رد قبل از تبدیل به long | ۱۵ |
| 100000000001 | رد بالای سقف | ۱۵ |
| null (قیمت خالی) در ورودی decimal? | رد پیش از تبدیل و بدون محاسبه | ۱۵ |
| نام خالی | دادهٔ محصول نامعتبر | FR-001، FR-011 |

نوع معتبر محصول long است و مرز اعتبارسنجی decimal?؛ قیمت خالی فقط null است، نه رشتهٔ
خالی. آزمون کسری/null و محدوده قبل از تبدیل به long انجام شود. مقادیر ۱ تا ۴ به دلیل
ایجاد قسط صفر رد شوند؛ ۵ و ۱۰۰ میلیارد تومان مرزهای مجازند و جدول مالی آن‌ها را پوشش می‌دهد.
ورودی غیرعددی، رشتهٔ خالی، متن و NaN/Infinity سناریوی این مرز عددی نیستند؛ هیچ parser
عمومی برای آن‌ها ساخته نشود. سناریوی کسری نباید با truncate به ۵ تومان بدل شود.

### روز تهران و ساعت مستقل

TimeProvider با UTC ثابت تزریق شود؛ از DateTime.Now سیستم یا ساعت مرورگر استفاده نشود.

| UTC ثابت | انتظار |
| --- | --- |
| 2026-10-08T12:00:00Z | baseDate = 1405/07/16؛ جدول اول سررسید |
| 2026-10-08T20:29:59Z | baseDate = 1405/07/16 |
| 2026-10-08T20:30:00Z | baseDate = 1405/07/17؛ چهار سررسید با روز ۱۷ |

دو درخواست دو طرف نیمه‌شب نتیجهٔ متفاوت و no-store دارند؛ یک درخواست حتی اگر ساعت
جعلی با هر بار خواندن تغییر کند، فقط یک snapshot از ساعت می‌خواند. تغییر TZ ماشین یا منطقهٔ
زمانی مرورگر نباید پاسخ را عوض کند. این آزمون‌ها FR-012 و سناریوی ۱۱ را پوشش می‌دهند.
تاریخ غیرقابل تبدیل یا خارج از محدوده باید خطا بدهد، نه fallback به UTC/میلادی.

## API integration، WebApplicationFactory

- سناریوهای ۱/۲/۵: GET محصول و برنامه بدون auth، 200؛ JSON contract و no-store درست؛
  snapshot محصول با قیمت مبنای برنامه برابر؛ چهار قسط و metadata صحیح؛ SC-001.
- DI محصول با پنج قیمت جدول و ساعت ثابت: response مبالغ string داشته باشد، نه JSON number؛
  سقف کامل serialize شود، جمع دقیق باشد؛ FR-002، SC-003.
- DI محصول مفقود: 404 product_not_found؛ نام/قیمت نامعتبر: 500 invalid_product؛ به ازای
  تمام ورودی‌های جدول رد، عدم نمایش برنامه و ProblemDetails بررسی شود؛ سناریوهای ۶/۱۴/۱۵.
- با ساعت ثابت و محصول یکسان، query مانند priceToman=5، baseDate=1400/01/01 یا foo=bar
  باید 200 و دقیقاً همان snapshot درخواست بدون query بدهد؛ پارامترها بی‌اثرند. body روی GET
  همچنان 400 invalid_request است. endpoint نوشتن وجود نداشته باشد؛ FR-010 و FR-014.
- calculator با exception تستی: 500؛ code مشخص، بدون stack trace و بدون برنامهٔ ناقص؛ FR-011.
- no-store و snapshot روز تهران دو طرف نیمه‌شب بررسی شود؛ آزمون API هم‌زمان با ساعت واقعی اجرا نشود.
- expiresAt در 2026-10-08T12:00:00Z و 2026-10-08T20:29:59Z برابر
  2026-10-08T20:30:00Z و در 2026-10-08T20:30:00Z برابر 2026-10-09T20:30:00Z
  است؛ expiry نیمه‌شب تهران است، نه زمان درخواست + ۲۴ ساعت. serverTime از همان snapshot UTC، UTC Z و فیلدهای الزامی
  مطابق schema بررسی شوند؛ FR-015.

## فرانت‌اند و مرورگر

Vitest برای parser/formatter: پاسخ معتبر، فیلد required مفقود، عدد به‌جای رشتهٔ مبلغ، قسط مفقود،
metadata غلط و serverTime/expiresAt نامعتبر یا پاسخ validity بدشکل را تفکیک کند؛ formatter پنج مثال جدول، به‌خصوص سقف،
دقیق و بدون اعشار باشد. کنترل جمع و دامنهٔ مالی در بک‌اند و آزمون قرارداد باقی بماند؛
در مرورگر BigInt، جمع پرداخت‌ها یا افزودن ماه برای جبران پاسخ وجود ندارد.

### آزمون قرارداد خطا و فیلدهای اختیاری، Vitest

- پاسخ HTTP500 با type/title/status/detail/code معتبر و بدون errors پذیرفته شود؛
  نبود فیلد اختیاری باعث خطای parser یا جایگزینی پیام معتبر با پیام عمومی نشود.
- همان پاسخ با errors معتبر مانند `{ "priceToman": ["قیمت نامعتبر است"] }` و با
  object خالی پذیرفته شود.
- errors حاضر با null، آرایه، مقدار غیرآرایه یا عضو غیررشته رد و پیام عمومی نمایش داده شود.
- حذف هر یک از پنج فیلد required یا ناسازگاری status با HTTP پاسخ را نامعتبر کند؛
  هیچ فیلد خارج از required صرفاً به‌دلیل نبودن الزامی نشود.

### تست خودکار کامپوننت با React Testing Library و jsdom

آزمون‌ها DOM و رفتار کاربر را بررسی کنند؛ snapshot داخلی state یا mock تابع محاسبات لازم نیست.
fetch mock، ساعت ثابت و fake timers در Vitest استفاده شوند؛ پس از هر تست پاک‌سازی شوند.

| مورد | انتظار قابل مشاهده | پوشش |
| --- | --- | --- |

اعتبارسنجی دستی مرورگر مکمل تست‌های خودکار بالا و طبق quickstart: SC-001/003/005، سناریوهای ۱/۲/۵؛ نمایش بدون ورود،
برچسب‌ها، چهار ردیف، تاریخ مبنا و مجموع؛ کلیک دوباره snapshot تازه بگیرد. توقف backend
پیام خطا بدهد و برنامهٔ قبلی را معتبر نشان ندهد. پوشش UI پیش از اعلام تکمیل گزارش شود؛
موفقیت تست‌های backend جای این بررسی را نمی‌گیرد.

## رفع I1 — ساعت سرور، تأخیر و تعلیق

این تست‌ها فقط طراحی‌اند. Date.now و performance.now جدا mock شوند؛ fake timer یکسان
برای هر دو، استقلال ساعت‌ها را اثبات نمی‌کند. در نمونهٔ عددی، expiresAt−serverTime=60000ms،
m0=1000 و m1=3000، RTT=2000 و R=58000ms است؛ در m=33000 باقی‌مانده28000ms،
در m=61000 صفر است. این بودجه محافظه‌کارانه است، نه تخمین RTT/2.

| سناریوی خودکار | انتظار |
| --- | --- |
| Date.now یک روز عقب و یک روز جلو، monotonic ثابت | بودجه و نتیجه در هر دو یکسان، مطابق اختلاف serverTime/expiresAt |
| پرش ساعت تقویمی جلو/عقب حین نمایش | timer/اعتبار هیچ تغییر ناشی از پرش نکند |
| RTT=0، RTT=2000 و شبکه نامتقارن با مجموع همان2000 | بودجه به‌ترتیب60000،58000 و58000؛ تقسیم بر۲ ممنوع |
| پاسخ60000ms یا بیشتر تأخیر داشته باشد | R=0؛ برنامه هرگز ready نشود |
| expiry<=serverTime | برنامه نامعتبر و پنهان؛ بدون درخواست GET جدید خودکار |
| زمان یکنواخت از1000 تا61000 طی شود | اعتبار با مثال بالا تمام؛ اختلاف ساعت تقویمی بی‌اثر |
| توقف performance.now در تعلیق و عبور نیمه‌شب در سرور | بازگشت ابتدا checking و POST validity؛ پاسخ false برنامه را منقضی کند |
| درخواست برنامه یا validity در تعلیق pending و performance.now متوقف باشد | بودجهٔ پاسخ قدیمی رد؛ پس از بازگشت checking و بررسی تازهٔ همان snapshot، نه ready مستقیم |
| بررسی اعتبار هنوز pending است | نام/قیمت باقی، هیچ برنامهٔ قبلی معتبر نمایش داده نشود |
| بررسی true، بودجهٔ تازه مثبت و همان snapshot | فقط همان برنامه بازنمایش؛ GET برنامه و calculator هرگز صدا زده نشوند |
| بررسی false یا true که پاسخ آن تا تمام شدن بودجه تأخیر دارد | برنامه پنهان/expired؛ محاسبه فقط با اقدام کاربر |
| شکست بررسی شبکه، HTTP500 یا JSON خراب | verification-error؛ برنامه پنهان بماند، بررسی مجدد فقط POST validity |
| چند رویداد هم‌زمان visible/focus/pageshow | یک بررسی در جریان؛ هیچ محاسبهٔ GET خودکار |
| بررسی قدیمی پس از محاسبهٔ دستی برنامهٔ تازه برسد | پاسخ snapshot قدیمی برنامهٔ تازه را تغییر ندهد |

### قرارداد بررسی اعتبار، xUnit / WebApplicationFactory

در `ValidityApiTests.cs` درخواست baseDate=1405/07/16 و expiresAt=2026-10-08T20:30:00Z
با serverTime ثابت2026-10-08T20:29:59Z true و با20:30:00Z false باشد. روز قبلی/آینده و
expiry ناسازگار false؛ JSON/فیلد اضافی یا مفقود، روز شمسی ناموجود و timestamp غیر UTC Z
400 invalid_request. پاسخ200 فقط baseDate/serverTime/expiresAt/isValid و no-store باشد.
spy شمارش calculator باید در تمام بررسی‌ها صفر باشد؛ endpoint منبع محصول یا برنامهٔ
جدید نمی‌سازد و مبلغ/اقساط برنمی‌گرداند. پاسخ500 بررسی در کامپوننت مجوز ready نیست.
