# Test Design: استخراج از معیارهای پذیرش

این سند طراحی آزمون است؛ فایل تست یا implementation ندارد. مقادیر expected باید ثابت
باشند و با اجرای Calculator تحت آزمون تولید نشوند. شمارهٔ سناریوها به spec.md ارجاع دارد.

## محاسبات، xUnit

| قیمت P | پیش‌پرداخت D | هر یک از سه قسط اول B | قسط چهارم L | سناریو |
| --- | --- | --- | --- | --- |
| 1000000 | 300000 | 175000 | 175000 | ۲ |
| 1000010 | 300003 | 175001 | 175004 | ۳؛ باقی‌ماندهٔ ۳ تومان |
| 1000001 | 300000 | 175000 | 175001 | ۷؛ پیش‌پرداخت کسری |
| 5 | 1 | 1 | 1 | ۱۲؛ مرز پایین |
| 100000000000 | 30000000000 | 17500000000 | 17500000000 | ۱۳؛ مرز بالا |

هر ردیف باید علاوه بر پنج مبلغ، جمع دقیق، مثبت بودن چهار قسط، سود/کارمزد صفر و عدم
overflow را اثبات کند (FR-003 تا FR-007، FR-013، SC-002). برای D rounding، expected را
از جدول بردارید، نه از تبدیل double. کنترل اضافی روی نمونه‌های قیمت صحیح معتبر: سه قسط
اول برابر، اختلاف L با B بین صفر و سه، جمع مساوی P. این کنترل مکمل مثال‌های ثابت است.

| ورودی خام منبع | انتظار | سناریو |
| --- | --- | --- |
| 1، 2، 3، 4 | رد؛ چهار قسط مثبت ممکن نیست | ۱۴ |
| 0، -1 | رد | ۱۵ |
| 5.5 (decimal) | رد قبل از تبدیل به long | ۱۵ |
| 100000000001 | رد بالای سقف | ۱۵ |
| null در ورودی decimal? | رد بدون محاسبه | ۱۵ |
| نام خالی | دادهٔ محصول نامعتبر | FR-001، FR-011 |

نوع معتبر محصول long است و مرز اعتبارسنجی decimal?؛ آزمون کسری/null قبل از تبدیل به
long انجام شود. هیچ parser عمومی برای متن/NaN/Infinity ساخته نشود. غیرعددی در مدل typed
قابل نمایش نیست؛ اگر منبع قابل ساخت نباشد، برنامهٔ معتبر ارائه نمی‌شود. سناریوی کسری نباید
با truncate به ۵ تومان بدل شود.

### روز تهران و ساعت مستقل

TimeProvider با UTC ثابت تزریق شود؛ از DateTime.Now سیستم یا ساعت مرورگر استفاده نشود.

| UTC ثابت | انتظار |
| --- | --- |
| 2026-10-08T12:00:00Z | baseDate = 1405/07/16؛ جدول اول سررسید |
| 2026-10-08T20:29:59Z | baseDate = 1405/07/16 |
| 2026-10-08T20:30:00Z | baseDate = 1405/07/17؛ چهار سررسید با روز ۱۷ |

دو درخواست دو طرف نیمه‌شب نتیجهٔ متفاوت و no-store دارند؛ یک درخواست حتی اگر ساعت
جعلی با هر بار خواندن تغییر کند، فقط یک snapshot از ساعت می‌خواند. تغییر TZ ماشین یا منطقهٔ
زمانی مرورگر نباید پاسخ را عوض کند. این آزمون‌ها FR-012 و سناریوی ۱۱ را پوشش می‌دهند.
تاریخ غیرقابل تبدیل یا خارج از محدوده باید خطا بدهد، نه fallback به UTC/میلادی.

## API integration، WebApplicationFactory

- سناریوهای ۱/۲/۵: GET محصول و برنامه بدون auth، 200؛ JSON contract و no-store درست؛
  snapshot محصول با قیمت مبنای برنامه برابر؛ چهار قسط و metadata صحیح؛ SC-001.
- DI محصول با پنج قیمت جدول و ساعت ثابت: response مبالغ string داشته باشد، نه JSON number؛
  سقف کامل serialize شود، جمع دقیق باشد؛ FR-002، SC-003.
- DI محصول مفقود: 404 product_not_found؛ نام/قیمت نامعتبر: 500 invalid_product؛ به ازای
  تمام ورودی‌های جدول رد، عدم نمایش برنامه و ProblemDetails بررسی شود؛ سناریوهای ۶/۱۴/۱۵.
- با ساعت ثابت و محصول یکسان، query مانند priceToman=5، baseDate=1400/01/01 یا foo=bar
  باید 200 و دقیقاً همان snapshot درخواست بدون query بدهد؛ پارامترها بی‌اثرند. body روی GET
  همچنان 400 invalid_request است. endpoint نوشتن وجود نداشته باشد؛ FR-010 و FR-014.
- calculator با exception تستی: 500؛ code مشخص، بدون stack trace و بدون برنامهٔ ناقص؛ FR-011.
- no-store و snapshot روز تهران دو طرف نیمه‌شب بررسی شود؛ آزمون API هم‌زمان با ساعت واقعی اجرا نشود.
- expiresAt در 2026-10-08T12:00:00Z و 2026-10-08T20:29:59Z برابر
  2026-10-08T20:30:00Z و در 2026-10-08T20:30:00Z برابر 2026-10-09T20:30:00Z
  است؛ expiry نیمه‌شب تهران است، نه زمان درخواست + ۲۴ ساعت. UTC Z و فیلد الزامی
  مطابق schema بررسی شوند؛ FR-015.

## فرانت‌اند و مرورگر

Vitest برای parser/formatter: پاسخ معتبر، فیلد مفقود، عدد به‌جای رشتهٔ مبلغ، قسط مفقود،
metadata غلط و expiresAt نامعتبر را تفکیک کند؛ formatter پنج مثال جدول، به‌خصوص سقف،
دقیق و بدون اعشار باشد. کنترل جمع و دامنهٔ مالی در بک‌اند و آزمون قرارداد باقی بماند؛
در مرورگر BigInt، جمع پرداخت‌ها یا افزودن ماه برای جبران پاسخ وجود ندارد.

### تست خودکار کامپوننت با React Testing Library و jsdom

آزمون‌ها DOM و رفتار کاربر را بررسی کنند؛ snapshot داخلی state یا mock تابع محاسبات لازم نیست.
fetch mock، ساعت ثابت و fake timers در Vitest استفاده شوند؛ پس از هر تست پاک‌سازی شوند.

| مورد | انتظار قابل مشاهده | پوشش |
| --- | --- | --- |
| بارگذاری محصول و کلیک مشاهده | نام/قیمت، پیش‌پرداخت، چهار ردیف مبلغ/سررسید، مجموع و تاریخ مبنا؛ بدون ورود | ۱، ۲، ۵، ۱۶ |
| مثال مالی سقف در پاسخ | نمایش دقیق مبالغ، تومان و بدون اعشار | ۱۳، SC-003 |
| درخواست دوباره و خطای شبکه یا ProblemDetails | برنامهٔ قبلی پنهان؛ نام/قیمت معتبر باقی؛ پیام و تلاش مجدد | ۶، ۱۹ |
| کلیک تلاش مجدد پس از خطای برنامه | فقط endpoint برنامه دوباره فراخوانی و پاسخ معتبر نمایش داده شود | ۱۹، FR-016 |
| JSON خراب یا شکل پاسخ نادرست | خطای قابل فهم، بدون برنامهٔ ناقص | ۶، FR-011 |
| یک میلی‌ثانیه قبل از expiresAt | برنامه معتبر باقی بماند | FR-015 |
| رسیدن دقیق به expiresAt | مبالغ و جدول برنامه پنهان، محصول باقی، پیام انقضا و محاسبهٔ دوباره؛ هیچ fetch خودکاری نشود | ۱۷ |
| بازگشت focus/visibility/pageshow پس از expiry با timer معلق | برنامه پیش از نمایش دوباره نامعتبر شود؛ بدون fetch | ۱۸ |
| پاسخ دریافتی که از قبل منقضی است | هرگز برنامهٔ معتبر نمایش داده نشود؛ حالت expired | Edge Cases |
| کلیک محاسبهٔ دوباره پس از انقضا | یک GET برنامه؛ پاسخ روز تازه و deadline تازه نمایش داده شود | ۲۰ |
| پاسخ قدیمی دیررس یا callback انقضای برنامهٔ قبلی | snapshot تازه بازنویسی یا اشتباهاً منقضی نشود | FR-016 |
| unmount | timer و event listener باقی نمانند و fetch تازه ایجاد نشود | چرخهٔ کامپوننت |

اعتبارسنجی دستی مرورگر مکمل تست‌های خودکار بالا و طبق quickstart: SC-001/003/005، سناریوهای ۱/۲/۵؛ نمایش بدون ورود،
برچسب‌ها، چهار ردیف، تاریخ مبنا و مجموع؛ کلیک دوباره snapshot تازه بگیرد. توقف backend
پیام خطا بدهد و برنامهٔ قبلی را معتبر نشان ندهد. پوشش UI پیش از اعلام تکمیل گزارش شود؛
موفقیت تست‌های backend جای این بررسی را نمی‌گیرد.
