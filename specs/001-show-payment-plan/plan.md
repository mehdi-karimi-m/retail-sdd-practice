## Summary

یک صفحهٔ React/TypeScript نام و قیمت محصول نمونه را از ASP.NET Core دریافت می‌کند و با
درخواست مشاهدهٔ برنامه، پیش‌پرداخت، چهار قسط، تاریخ مبنا و مجموع را نشان می‌دهد.
دو endpoint از نوع Minimal API برای دریافت محصول/برنامه و یک endpoint بدون اثر جانبی برای بررسی اعتبار، یک محاسبه‌گر مستقل و یک منبع محصول در حافظه کافی‌اند.
محاسبات پول و تقویم فقط در بک‌اند انجام می‌شوند؛ دیتابیس و ذخیرهٔ برنامه لازم نیست.

## Technical Context

**Language/Version**: C# 14 / net10.0؛ TypeScript 6.0.2 با strict و target ES2022.

**Primary Dependencies**: ASP.NET Core 10.0.12 با SDK موجود 10.0.112؛ React/React DOM 19.3.0؛
Vite 8.3.3 و plugin-react 6.1.2؛ Node 24.18.0 و npm 11.16.0 موجود.
نسخه‌های پیشنهادی و منابع رسمی در [research.md](research.md) آمده‌اند.

**Storage**: هیچ دیتابیس، ORM، migration یا ذخیرهٔ برنامه/سفارش؛ یک محصول ثابت نمونه
(نام «محصول نمونه»، قیمت ۱٬۰۰۰٬۰۰۰ تومان) در منبع فقط‌خواندنی بک‌اند.

**Testing**: xUnit.net v3 با بستهٔ پایدار xunit.v3 4.0.1؛ آزمون HTTP با
Microsoft.AspNetCore.Mvc.Testing 10.0.12؛ Vitest 5.0.3 برای مرز قرارداد و نمایش مبالغ؛ React Testing Library و jsdom برای تست
خودکار کامپوننت، تلاش مجدد و انقضا؛ بررسی دستی مرورگر مکمل این تست‌ها است. داده‌های قطعی در [test-design.md](test-design.md).

**Target Platform**: Ubuntu 24.04 موجود، ASP.NET Core روی Linux و مرورگرهای جدید؛
ICU و tzdata برای Asia/Tehran لازم‌اند؛ حالت globalization invariant استفاده نشود.

**Project Type**: یک برنامهٔ وب با یک پروژهٔ اجرایی بک‌اند، یک پروژهٔ تست و یک فرانت‌اند.

**Performance Goals**: محاسبهٔ دقیق چهار قسط با کار ثابت و بدون I/O ذخیره‌سازی؛
مشخصات هدف بار یا تأخیر عددی تعیین نکرده و این طرح معیار پذیرش تازه اضافه نمی‌کند.

**Constraints**: قیمت صحیح ۵ تا ۱۰۰ میلیارد تومان؛ پول از نوع long و JSON string؛
ماه شمسی، مبنا روز جاری تهران؛ تمام اختلاف فقط در قسط چهارم؛ بدون حساب/سفارش/پرداخت.

**Scale/Scope**: یک محصول نمایشی و یک صفحه؛ نمونه‌های قیمت دیگر فقط دادهٔ آزمون هستند،
نه فرم قیمت، انتخاب محصول، فهرست محصولات یا endpoint محاسبهٔ دلخواه.

### جریان داده و نمایش

1. هنگام ورود صفحه، GET /api/product نام و قیمت معتبر محصول را می‌دهد.
2. کاربر «مشاهدهٔ برنامهٔ پرداخت» را انتخاب می‌کند؛ GET /api/product/payment-plan
   محصول و کل برنامه را به‌صورت یک snapshot برمی‌گرداند.
3. قیمت و تاریخ ورودیِ کاربر در API وجود ندارند. queryهای ناشناخته نادیده گرفته شوند؛
   حتی priceToman یا baseDate نباید قیمت یا تاریخ سرور را تغییر دهند. body ورودی دو GET
   نیست و همچنان رد می‌شود؛ POST validity فقط دو فیلد snapshot قبلی را می‌گیرد. برای داده‌های تست فقط از DI استفاده شود.
4. ساعت UTC یک‌بار در هر درخواست برنامه خوانده و به Asia/Tehran تبدیل می‌شود. تاریخ بدون
   زمان استخراج می‌شود. هر due date از همان تاریخ پایه تعیین می‌شود، نه از قسط قبلی.
5. پاسخ برنامه no-store است؛ هر مشاهدهٔ تازه دوباره درخواست می‌فرستد. هیچ ذخیرهٔ localStorage
   یا cache برنامه وجود ندارد. برنامهٔ نمایش‌داده‌شده تاریخ مبنای خودش را نشان می‌دهد؛
   backend در پاسخ serverTime از همان snapshot ساعت UTC و expiresAt را برابر نیمه‌شب بعدی تهران به UTC ارسال می‌کند. با رسیدن
   این زمان، برنامهٔ باز منقضی و پنهان می‌شود؛ پیام انقضا و دکمهٔ محاسبهٔ دوباره نشان داده
   شوند، ولی هیچ fetch یا محاسبهٔ خودکاری انجام نشود. پاسخ رسیده پس از انقضا هم نمایش داده نشود.
6. وضعیت محصول (loading/ready/error) از وضعیت برنامه (idle/loading/ready/error/expired/checking/verification-error)
   جدا نگه داشته شود. نام و قیمت معتبر در انتظار، خطا و انقضا باقی بمانند. درخواست تازه
   برنامهٔ قبلی را کنار بگذارد؛ پاسخ درخواست قدیمی با AbortController یا شناسهٔ درخواست
   نتواند پاسخ جدید را بازنویسی کند. تلاش مجدد برنامه فقط endpoint برنامه را فراخوانی کند.
7. پاسخ در runtime با type guard ساده فقط از نظر ساختار بررسی شود: رشتهٔ رقم برای مبلغ،
   چهار قسط شماره‌دار، شکل تاریخ‌ها، serverTime و expiresAt معتبر UTC و metadata مصوب. محاسبات جمع،
   فرمول و کنترل دامنهٔ مالی فقط در بک‌اند و آزمون قرارداد باشند؛ BigInt یا جمع پول در
   مرورگر لازم نیست. فقط فیلدهای required هر schema در مدل TS و type guard الزامی باشند؛
   `ProblemDetails.errors?: Record<string, string[]>` اختیاری است و نبود آن باعث رد خطای
   معتبر نشود. در صورت وجود errors، object بودن و آرایهٔ رشته بودن هر مقدار بررسی شود.
   پاسخ با ساختار ناسازگار، حتی HTTP 200، پیام خطای عمومی بدهد.
8. ارقام رشته‌ها با گروه‌بندی سه‌رقمی و تبدیل نمایشی به ارقام فارسی همراه «تومان» نشان داده شوند؛
   Number، parseFloat و گرد کردن در مرورگر استفاده نشوند. تاریخ شمسی رشته‌ای مستقیماً نمایش
   داده شود؛ Date.parse یا Date constructor روی تاریخ شمسی اجرا نشود. فقط serverTime و expiresAt
   به‌عنوان timestamp UTC برای اختلاف زمانی parse شوند؛ مقایسه با Date.now ممنوع است. timer انقضا و بررسی visibilitychange،
   focus و pageshow از نمایش دوبارهٔ snapshot منقضی جلوگیری کنند؛ این رخدادها فقط بررسی اعتبار انجام دهند، نه GET محاسبهٔ برنامه.
   timerها با تعویض برنامه یا unmount پاک شوند و callback قدیمی برنامهٔ تازه را منقضی نکند.

### اعتبارسنجی و خطا

نام محصول نباید خالی باشد. منبع فقط‌خواندنی ورودی قیمت decimal دقیق (nullable برای دادهٔ
مفقود) ارائه کند؛ مقدار کسری، مفقود، غیرمثبت، زیر ۵ یا بالای سقف پیش از تبدیل به long رد شود.
parser عمومی متن/NaN/Infinity یا adapter برای منبع آینده اضافه نشود؛ decimal این مقادیر را
نمایندگی نمی‌کند. اگر مدل منبع نتواند ساخته شود، خطای منبع است، نه تغییر بی‌صدای قیمت.
محاسبه در checked انجام و مثبت بودن چهار قسط و برابری مجموع کنترل شود.
دادهٔ داخلی نامعتبر 500 با code=invalid_product و محصول مفقود 404 است. body نامجاز 400 است؛
query ناشناخته نادیده گرفته می‌شود؛
استثنا یا invariant خراب 500 است. تمام این پاسخ‌ها application/problem+json با code و
پیام فارسی قابل نمایش‌اند؛ جزئیات stack trace به مشتری نرود. ثبت فنی سمت سرور کافی است.
خرابی ساعت، تقویم یا تبدیل منطقهٔ زمانی نباید به تاریخ UTC یا تقویم دیگر fallback کند.
نبود ICU/tzdata لازم در شروع اجرا خطای صریح راه‌اندازی بدهد.

در توسعه Vite مسیر /api را به localhost:5080 proxy می‌کند، پس CORS عمومی لازم نیست.
در اجرا با یک origin، فایل‌های ساخته‌شده می‌توانند توسط ASP.NET Core ارائه شوند؛ استقرار
و میزبانی در دامنهٔ این قابلیت طراحی یا اجرا نمی‌شوند.

### اعتبار زمانی برنامه — تصمیم I1

بک‌اند در پاسخ برنامه serverTime و expiresAt را با UTC Z ارسال کند. یک snapshot ساعت
TimeProvider مبنای هر دو و baseDate است؛ expiry نیمه‌شب شروع روز بعد تهران است، نه now+24h.
زمان مرجع مربوط به ساخت پاسخ است، نه زمان ساعت دستگاه. cache تمام پاسخ‌های زمانی no-store باشد.

در فرانت‌اند m0=performance.now پیش از fetch و m1 پس از دریافت/parse کامل پاسخ ثبت شود.
RTT=m1−m0؛ بودجهٔ محافظه‌کارانه R=max(0,parse(expiresAt)−parse(serverTime)−RTT).
در لحظهٔ m>=m1، باقی‌مانده max(0,R−(performance.now−m1)) است. تمام RTT کسر شود، نه
RTT/2؛ زمان ارسال دقیق پاسخ معلوم نیست و این انتخاب ممکن است تا یک RTT زودتر نمایش را
متوقف کند، اما تأخیر را به عمر برنامه اضافه نمی‌کند. R=0 هرگز ready نشود. Date.now، ساعت
تقویمی دستگاه و performance.timeOrigin مرجع اعتبار نیستند. timer فقط بیدارسازی است و
callback باید باقی‌مانده را دوباره از ساعت یکنواخت حساب کند.

هنگام hidden شدن، pagehide یا freeze، نمایش snapshot نیازمند تأیید علامت بخورد؛ هنگام
visible/focus/pageshow/resume، پیش از نمایش دوباره به checking برود و POST
/api/product/payment-plan/validity را با baseDate و expiresAt همان snapshot بفرستد.
اگر lifecycle پس از توقف بدون اعلان اولیه فعال شد، باز هم checking مقدم بر نمایش است.
هر درخواست زمان‌دار یک شناسهٔ دورهٔ فعال lifecycle ثبت کند؛ اگر بین ارسال و پاسخ تعلیق
یا غیرفعال‌شدن رخ دهد، بودجهٔ آن پاسخ قابل اعتماد نیست و مجوز ready نیست؛ پس از بازگشت
همان snapshot با validity در دورهٔ فعال تازه بررسی شود. performance.now ممکن است در تعلیق متوقف شود؛ بودجهٔ قبل از تعلیق قابل اعتماد نیست و
از آن برای بازنمایش بدون سرور استفاده نشود. رخدادهای هم‌زمان یک بررسی در جریان داشته باشند.

endpoint اعتبار بدون دیتابیس، بدون خواندن/محاسبهٔ اقساط و بدون تغییر محصول، زمان مرجع
فعلی را می‌خواند؛ expiry استاندارد روز baseDate را استخراج و با expiry ارسالی تطبیق می‌دهد.
isValid فقط برای روز مبنای برابر امروز تهران، expiry صحیح و serverTime<expiry درست است.
برنامهٔ روز گذشته/آینده یا expiry دستکاری‌شده false می‌گیرد؛ دادهٔ بدشکل/نامعتبر 400.
پاسخ فقط baseDate،serverTime،expiresAt استاندارد و isValid دارد، نه برنامهٔ تازه. تاریخ
ارسالی فقط برای بررسی snapshot است، نه تعیین تاریخ خرید یا محاسبهٔ برنامهٔ دلخواه.

در پاسخ true نیز RTT لحاظ و بودجهٔ تازه فقط برای همان snapshot ثبت شود؛ باقی‌ماندهٔ صفر
یا false به expired می‌رود. شکست شبکه/JSON/سرور به verification-error می‌رود و برنامه
پنهان می‌ماند؛ «بررسی دوبارهٔ اعتبار» فقط validity را تکرار کند. «محاسبهٔ دوباره» فقط با کلیک
کاربر GET برنامه را اجرا می‌کند. نام/قیمت معتبر در checking، خطا و انقضا باقی بمانند.

شناسهٔ نسل snapshot/درخواست مانع اثر پاسخ validity یا timer قدیمی روی برنامهٔ جدید شود؛
unmount listener/timer/request را پاک یا لغو کند. POST بررسی اثر تجاری/ذخیره‌سازی ندارد.
